# Shimla Futuristic Property Management PWA Implementation Plan

## Goal Description
Build a secure, private, minimalist property management dashboard for the Shimla Building. The app currently features a vertical list of floors and their respective units, with an aesthetically pleasing "Apple-style" futuristic minimalist design.

This phase extends the application with:
1. An interactive, visual block-style Building Map at the top of the interface.
2. A Data Dashboard with animated graphs (Recharts), financial summaries, and real-time filtering (by Floor, Unit, Electricity #, Water #).

### Phase 6: Tenant History Tracking (Active)
- **Extending the Schema:** Expand each unit object in `buildingLayout` to contain an array of `tenantHistory` objects (mapping name, details, and exact tenure).
- **Dedicated View Component:** A full-bleed tabular application (`HistoricalTenants.jsx`) specifically designed to quickly parse strings (names, companies) over integers (rent).
- **Multi-Sheet Syncing:** The `sync.js` google sheet hook must gracefully expand to manage multiple parallel sub-sheets (Monthly Ledger vs Tenant List).

### Phase 7: Tenant Management & Onboarding (Active)
- **Tenant Modals:** Create a `TenantManagementModal` UI allowing the user to select a Unit and either 1) Add a new Tenant or 2) Remove the current Tenant.
- **Historical Logic:** When a new tenant is added or an active tenant removed, the systemic `buildingLayout` must close the loop on the old tenant by attaching today's timestamp to their `leaveDate`, and appending the new tenant with a `joinDate`.
- **Data Scrubbing:** Eliminate all the fake mock tenants from `buildingLayout.js` while keeping the structural hierarchy of the building (floors/units), paving the way for real data entry.

### Phase 8: Pure Cloud Architecture (Google Sheets Hydration) [DEPRECATED]
- **Source of Truth Shift:** Google Sheets backend proved conceptually unstable due to HTTP Proxy hydration crashes on uninitialized Netlify Dev servers.
- Deprecated in favor of Phase 9.

### Phase 9: Firebase NoSQL Architecture Migration (Active)
- **SDK Integration:** Drop fragile HTTP REST fetching (Netlify Functions) and inject the native `@firebase/app` and `@firebase/firestore` SDK directly into the React client.
- **Database Schema:** Convert the "Flat Sheets" into NoSQL collections:
  - `Units` Collection: Core configuration (Meter IDs, base rent).
  - `Tenants` Sub-collection or Object Array: Historical log of occupants (Join/Leave dates).
  - `Ledger` Collection: Specific monthly data logs mapping to `UnitID` and `BillingMonth`.
- **Real-Time Hydration:** Re-write `App.jsx` to hydrate directly from `getDocs` against Firestore, completely eliminating the JSON parsing 500 errors.
- **Cleanup:** Delete `netlify/functions/*` and `google-spreadsheet` from dependencies to drastically reduce bundle size and server complexity.

### Phase 10: Interactive Ledger Table & Export (Active)
- **Feature Scope**: Build a highly-dense data table component (`LedgerTable.jsx`) to functionally replace the loss of the raw Google Sheets view. Place this interface prominently beneath the visual map/dashboard on the Home view.
- **Filtering System**: Above the table, place dropdowns/inputs for:
  - `BillingMonth` (Default to current, optionally "All Time")
  - `Floor` OR `Unit Type`
  - `Rent Status` (Paid/Unpaid)
- **Export capabilities**: Evaluate integrating lightweight client-side libraries (`jspdf` and `jspdf-autotable` for PDF layout, and simple Blob generation for CSV/Excel export) to allow building managers to download physical copies of the filter results.

### Phase 11: Real-World Physical Architecture Mapping (Active)
- **Scope**: Entirely wipe the mock JSON tree from `buildingLayout.js` and hardcode the application to map against the real 6-floor physical architecture.
- **Structural Plan**:
  1. **Basement**: 2 Units (`Studio 1`, `Studio 2`)
  2. **Ground Floor**: 2 Units (`2RK AirBnB`, `2RK Flat`)
  3. **First Floor**: 4 Units (`2RK Flat`, `Single Room 1`, `Single Room 2`, `3-Room Unit`)
  4. **Second Floor**: 1 Unit (`Silver Oak BnB` - Full Floor)
  5. **Third Floor**: 1 Unit (`Private Residence`)
  6. **Fourth Floor**: 1 Unit (`Private Residence - Attic`)
- **Execution Hook**: After modeling this locally, we must execute a master Firebase wipe and push this new blank layout upward to act as the new foundation.

### Phase 12: Ground Floor Expansion & Level Shift (Completed)
- **Scope**: Add a new floor above the Basement and below the original Ground Floor to house a `1BHK Flat` and a `Single Room`.
- **Methodology**: 
  - The previous Ground Floor (001, 002) was shifted up to become the 1st Floor (101, 102).
  - All subsequent floors were shifted up by 1 (+1 up to Level 5).
  - A surgical Firebase wipe script was deployed to completely scrub old IDs from `Units`, `Tenants`, and `Ledger` to prevent data-overlap before re-seeding the shifted architecture.

### Phase 13: Tenant Lifecycle & Future-Dating Engine (Completed)
- **Feature Scope**: Upgrade `TenantManagementModal.jsx` to explicitly handle three distinct lifecycle events: Add Tenant (to vacant unit), Replace Tenant (seamless handover), and Evict Tenant (move-out). Ensure all events support Future-Dated scheduling.
- **Architectural Shift (`isOccupied` Engine)**:
  - Previously, a unit was considered occupied if the tenant's `leaveDate` was `null` or `Current`.
  - **New Logic**: A tenant is globally considered "Active" if `!leaveDate` OR `leaveDate >= today()`.
  - When the calendar rolls over their scheduled `leaveDate`, the system will systematically transition the unit to Vacant or hand it over to the next scheduled tenant without manual intervention.
- **UI Upgrades**:
  - Implement a highly-visual, tabbed form in `TenantManagementModal` (Add, Replace, Evict).
  - Capture explicit Join/Leave dates. If replacing, coordinate the out-going Leave Date with the in-coming Join Date.

### Phase 14: Real-World Dataset Initialization (Completed)
- **Scope**: Wipe all dummy data and permanently initialize Firebase with the actual Tenant Names, Electricity Meter IDs, Water Meter IDs, and Garbage Sub IDs provided by the user.
- **Execution**: 
  - Ran `wipeFirebase.js` to clear the cloud.
  - Hardcoded the master data list into `buildingLayout.js`.
  - Reseeded `Units`, `Tenants`, and `Ledger` via script, initializing all active records to Jan 2026.
  - Upgraded the `fetchBuildingStateFromCloud` engine in `App.jsx` to dynamically inject the cloud's real-world Meter/Garbage IDs on load, making the UI an exact 1:1 reflection of the database.

### Phase 16: Analytics Refinement & Historical Data Guardrails (Active)
- **Scope**: Refine the Bulk Data Entry module to support a per-unit garbage/water inclusive toggle to replace the global one. Modify dashboard analytics to show specific unit tracking and utility trends from Jan 2026. 
- **Execution**:
  - `BulkDataEntry.jsx`: Add an `includesUtilities` boolean to the `draftData` row state, shifting the toggle from global to a per-row context. Add a `window.confirm` warning when `selectedMonth < currentMonth` to prevent accidental historical overwrites.
  - `Dashboard.jsx`: Remove floor-based revenue and 6-month aggregate collection charts. Introduce a new two-line graph plotting Water vs. Electricity bills historically per month starting from Jan 2026. Ensure top-level KPI cards accurately react to the existing global `FilterContext` (Unit, Floor, Meter selections). 
  - Change the global default application start state logic to Jan 2026 where applicable.

## Data Layer & Rent Cycles (Phase 3)
We are preparing the data pipeline for a future Google Sheets database backend starting from Jan 2026.

### Data Model Changes
- **Rent Cycles**: Instead of a static `rent` string, the data model will use a `rentHistory` array.
- Support specifying rent from `X month` to `Y month`.
- `currentRent` will be dynamically calculated based on the current date falling within a cycle.

### Expiration Alerts
- Implement a global check that flags rent cycles ending within 1 month.
- Show a popup alert/notification prompting the user to update the rent cycle.

### Google Sheets Pipeline Preparation
- Structure the local data mock to precisely match how rows and columns will be formatted in Sheets.

## Bulk Collection Operations (Phase 4)
We are replacing the static vertical directory list with a powerful bulk data entry pipeline optimized for speed at the end of every month.

### Bulk Data View Features
- **Month/Year Selector:** A global control for the specific billing month the user is currently processing.
- **Data Entry Grid:** A fast spreadsheet-like UI showing every specific unit that allows for rapid typing into the following fields simultaneously:
    - `Rent Status` (Paid/Unpaid dropdown)
    - `Rent Amount` (Auto-filled based on the dynamic rent cycle logic, but editable)
    - `Electricity Bill` (Input)
    - `Water Bill` (Input)
    - `Garbage Bill` (Input)
- **Mass Submit:** Pushes the entire updated object structure into the mock configuration (simulating what the Google Sheets pipeline will receive under one API call).
